<p>Git is a distributed Version Control System (VCS) that allows us to track code changes, manage collaboration, and improve the development process. This article covers essential Git commands and explains how to leverage GitHub's pull request (PR) functionality for collaborative workflows. You don't need to memorize all the commands from this article. Treat it more like a cheat sheet because you have to learn Git through practice and real-world experience, and not only by reading.</p>

<h3><a id="basics">Basics</a></h3>

<p>A <b>repository</b> is a storage space for a project, including its full version history. A local repository resides on our computer, and a remote repository is hosted on a server (e.g., GitHub), allowing for collaboration and version control across multiple users. A <b>commit</b> is a snapshot of the project's changes at a specific point in time, capturing the modifications made to files and providing a unique identifier for tracking the history of those changes. <b>Branches</b> are parallel versions of the project that allow us to work on different features or fixes independently, enabling us to merge changes back into the main codebase without disrupting the primary workflow.</p>

<p>When we're ready to commit certain changes, we add ("<b>stage</b>") them to Git's <b>staging area</b> using ```git add```. The staging area holds a snapshot of these changes, preparing them for the commit. This allows us to control which changes go into each commit. The <b>working directory</b> is the local folder where we edit and save files. Any changes made here are untracked by Git until they are staged (into the staging area).</p>

<p>```HEAD``` is a pointer that references your current checked-out commit (usually through the current branch). ```HEAD^``` refers to the parent of ```HEAD```, and ```HEAD^n``` refers to the <em>n</em>th parent of a merge commit (e.g., ```HEAD^2``` is the second parent). ```HEAD^``` refers to the parent commit of ```HEAD``` (the commit directly before it). ```HEAD~n``` refers to the commit that is <em>n</em> commits before ```HEAD``` by following the main history (first parent). For example, ```HEAD~2``` is two commits before ```HEAD```.</p>

<h3><a id="merge-conflicts">Merge conflicts</a></h3>
<p>A merge conflict occurs when two branches have competing changes to the same line of code or file, preventing automatic merging and requiring manual resolution.</p>

<p>If they arise, Git will mark the affected files. We can resolve these by editing the files, identifying conflict markers (```<<<<<<<```, ```=======```, ```>>>>>>>```), and deciding which changes to keep. Conflict markers are special annotations added to a file by Git to indicate the sections of code that are in conflict during a merge, typically showing the differing changes from each branch.</p>

```text
# Fetch updates from the main branch
git fetch origin main

# Switch to the main branch and merge with the feature branch
git switch main
git merge feature_branch

# Resolve conflicts manually in the files, then stage and commit the resolved files
git add [resolved_file]
git commit -m "Resolve merge conflicts in feature_branch"
```

<h3><a id="switching-to-a-specific-commit">Switching to a specific commit</a></h3>

<p>Sometimes we want to inspect or test the state of the repository at a specific commit. Each commit in Git has a unique hash (identifier), which allows us to move the repository to that exact point in the project history.</p>

<div className="table-container"><table>
    <tr>
        <td>```git checkout [commit-hash]```</td>
        <td>Switching to a specific commit using its unique identifier.</td>
    </tr>
    <tr>
        <td>```git switch --detach [commit-hash]```</td>
        <td>Switching to a specific commit in a detached HEAD state (modern Git command).</td>
    </tr>
    <tr>
        <td>```git switch -c [new-branch] [commit-hash]```</td>
        <td>Creating a new branch starting from a specific commit.</td>
    </tr>
</table></div>

<p>When we switch directly to a commit, Git enters a <b>detached HEAD state</b>. This means we are no longer on a branch but instead viewing the repository at that specific commit. This is useful for inspecting previous versions or testing older states of the project.</p>

<p>If we want to continue development from that commit, it is recommended to create a new branch from it using ```git switch -c```. Otherwise, any commits made in the detached state may become difficult to track.</p>

<h3><a id="pull-requests-on-github">Pull requests on GitHub</a></h3>
<p>A pull request (PR) is a GitHub feature that allows developers to propose, review, and discuss code changes before merging them into the main branch. It helps facilitate collaboration, enables code reviews, and improves overall code quality.</p>

<h5>Creating a pull request</h5>
<ol> <li>Create and switch to the feature branch: ```git switch -b feature-branch```.</li> <li>Make changes and commit them.</li> <li>Push the changes to the remote repository.</li> <li>On GitHub: <ul> <li>Navigate to the repository.</li> <li>Click "New Pull Request".</li> <li>Select branches.</li> <li>Fill the PR description using a template (if available).</li> <li>Add reviewers and labels.</li> </ul> </li> </ol>

<h5>PR best practices</h5>
<ul>
    <li>Keep PRs focused and reasonably sized.</li>
    <li>Write clear descriptions explaining: <ul> <li>What changes were made?</li> <li>Why changes were needed?</li> <li>How to test the changes?</li> <li>Any related issues or dependencies?</li> </ul> </li>
    <li>Respond to review comments promptly.</li>
    <li>Update PR with requested changes.</li>
    <li>Resolve conflicts when they arise.</li>
</ul>

<p>Reviewers can annotate lines and approve or request changes. This review process ensures code quality and promotes team collaboration. As changes are requested, additional commits can be made to the branch and pushed to the PR.</p>

<h3>```<a id="gitignore">.gitignore</a>```</h3>
<p>The ```.gitignore``` file is crucial for managing which files and directories Git should ignore in our repository. <h3><a id="forks">Forks</a></h3>
<p>A fork is a copy of a repository that allows us to freely experiment with changes without affecting the original project. This workflow is particularly useful in open-source development, where contributors don't have direct write access to the main repository. When we want to contribute to an open-source project, we have to fork the repository, which means creating a copy of the original repository under our GitHub account. This allows us to make changes, add features, or fix bugs independently without impacting the original codebase. After making our desired changes in our forked repository, we can submit a pull request to the original repository, proposing that our changes be reviewed and potentially merged into the main project. This process encourages collaboration and helps maintain the integrity of the original project while allowing contributors to experiment and innovate freely. To fork a repository on GitHub, log in to GitHub and navigate to the repository you want to fork, click the Fork button in the upper right corner, select your account if prompted, wait for the forking process to complete, access your forked repository under your GitHub account, and optionally clone your fork locally using ```git clone https://github.com/your-username/repository-name.git```.</p>

<h3><a id="rebasing">Rebasing</a> (```git rebase```)</h3>
<p>Rebasing is used to move or replay a sequence of commits from one base to another. This is commonly done to update a feature branch with the latest changes from the main branch while keeping a linear history. The flow is as follows:</p>

<div className="table-container"><table>
    <tr>
        <td>```git switch feature```</td>
        <td>Switching to the feature branch.</td>
    </tr>
    <tr>
        <td>```git fetch origin```</td>
        <td>Fetching the latest changes from the remote repository.</td>
    </tr>
    <tr>
        <td>```git rebase origin/main```</td>
        <td>Reapplying the feature branch commits on top of the latest main branch.</td>
    </tr>
</table></div>

<p>This rebased the current ```feature``` branch onto the latest ```origin/main``` by replaying its commits on top of it. This created a clean, linear commit history. The argument ```origin/main``` specifies the new base for the rebase. It is <b>not</b> the branch being modified. The branch that changes is the one we are currently on.</p>

<p>Rebasing is commonly used to update a local feature branch with the latest changes from the main branch before merging. It keeps the commit history clean and linear. Avoid rebasing branches that have already been shared with others because rebasing rewrites commit history. If merge conflicts occur during the rebase, resolve them and continue the process with ```git rebase --continue```.</p>

<h3><a id="interactive-rebasing">Interactive rebasing</a> (```git rebase -i```)</h3>
<p>Interactive rebasing is a powerful tool for cleaning up our commit history before sharing our code. It allows us to modify commits in various ways, including combining, editing, or removing them.</p>

<div className="table-container"><table>
    <tr>
        <td>```git rebase -i --root```</td>
        <td>Starting interactive rebase from the very first (root) commit of the repository.</td>
    </tr>
    <tr>
        <td>```git rebase -i HEAD~n```</td>
        <td>Starting interactive rebase for the last n commits.</td>
    </tr>
    <tr>
        <td>```git rebase -i [commit-hash]```</td>
        <td>Rebasing interactively from a specific commit.</td>
    </tr>
</table></div>

<p>```HEAD~n``` refers to a specific commit in Git's history, where ```HEAD``` represents the current commit and ```n``` is how many commits to go back. When used with ```git rebase -i```, the specified commit acts as the <strong>base</strong> - meaning it won't be edited itself, but all commits between it and ```HEAD``` will appear in the rebase editor. For example, ```HEAD~1``` rebases the last commit, ```HEAD~2``` rebases the last 2 commits, and so on.</p>

<h5>Examples</h5>
<h6>Interactive rebase session</h6>
```text
# Start interactive rebase
git rebase -i HEAD~5

# You'll see something like this in your editor:
pick 2231360 Add the initial login form
squash 3d4d2d1 Fix login form styling
fixup 2b504be Update login form padding
reword f7f3f6d Add form validation
edit cdd94dc Implement password reset
```

<p>When we run an interactive rebase, Git opens a text file in the default editor listing the selected commits, each prefixed with a command (defaulting to ```pick```). We edit this file by replacing the command word next to each commit to control what happens to it, then save and close the editor to start the rebase.</p>

<p className="noBottomMargin">The ```pick``` command indicates that the commit with the specified hash should be included in the final history as is.</p>
<p className="noBottomMargin">The ```squash``` command combines the specified commit with the previous one, allowing us to merge their changes and edit the commit message.</p>
<p className="noBottomMargin">The ```fixup``` command also combines the specified commit with the previous one, but it does so without prompting to edit the commit message.</p>
<p className="noBottomMargin">The ```reword``` command allows us to modify the commit message of the specified commit while keeping its changes intact.</p>
<p>The ```edit``` command pauses the rebase process at the specified commit, allowing us to make changes before continuing the rebase.</p>

<h6>Splitting a commit</h6>
```text
# During rebase, when stopped at 'edit'
git reset HEAD^
git add file1
git commit -m "First part of the split"
git add file2
git commit -m "Second part of the split"
git rebase --continue
```

<p className="noBottomMargin">Never rebase commits that have been pushed to public branches.</p>
<p className="noBottomMargin">Create a backup branch before complex rebases using ```git branch backup-branch```.</p>
<p className="noBottomMargin">Keep commits logically grouped.</p>
<p className="noBottomMargin">Write clear commit messages that explain the "why" not just the "what".</p>
<p>Test your code after completing the rebase.</p>

<h5>A real-world problem</h5>
<p>Suppose you are working on a branch and have made three commits: 1, 2, and 3. After testing, you realize that commits 2 and 3 introduced bugs and should not be included in the final branch. Instead of keeping the buggy changes, you want to go back to commit 1, make the correct changes, and create a new commit 4 that represents the fixed work. Using interactive rebase, you can drop commits 2 and 3, effectively removing them from the branch history. Then, apply your corrected changes and commit them as commit 4. This results in a clean history: 1 → 4, with the buggy commits completely skipped.</p>

<h3><a id="aliases">Aliases</a></h3>
<p>Creating Git aliases can significantly improve our workflow by allowing us to shorten frequently used commands. For example, we can set an alias for the checkout command with ```git config --global alias.co checkout```. This means we can simply type ```git co``` instead of ```git checkout```. Using aliases can save time and reduce the likelihood of errors when typing long commands.</p>
<p>We can set up useful aliases in ```.gitconfig```:</p>
```text
[alias]
co = checkout
br = branch
ci = commit
st = status
unstage = reset HEAD --
last = log -1 HEAD
```

<p>*```reset HEAD --``` - the two dashes indicate that what comes after is a file path.</p>

<h3><a id="hooks">Hooks</a></h3>

<p>Git hooks are scripts that Git runs before or after specific events in the workflow, enabling automation and policy enforcement within repositories. Located in the ```.git/hooks``` directory, these customizable scripts can validate commit messages, run tests before pushes, or trigger deployments after merges, helping teams maintain code quality and improve their development processes.</p>

<h3><a id="github-pages">GitHub pages</a></h3>

<p>GitHub Pages is a service provided by GitHub that allows us to host websites directly from our GitHub repositories. It is an easy and free way to publish static websites, such as personal portfolios, blogs, or project documentation. It supports HTML, CSS, and JavaScript, and it integrates seamlessly with GitHub repositories, meaning that any changes made to the repository automatically update the live website. We can choose to host our site from the root of the repository or a specific branch. Additionally, GitHub Pages provides custom domain support, allowing us to link our domains to our hosted websites.</p>
