<p>Structural design patterns deal with object composition and the organization of classes and objects. They help ensure that components in a system are arranged efficiently, promoting flexibility and reusability. They emphasize APIs to keep complex structures easy to manage and extend.</p>

<h2><a id="adapter">Adapter</a></h2>

<p>Adapter allows incompatible interfaces to work together by acting as a bridge between them. It translates one interface into another (adapts it), enabling classes with different APIs to communicate seamlessly without modifying their existing code. It is an in-between component.</p>

```java
public class Main {
    public static void main(String[] args) {
        OldPrinter oldPrinter = new OldPrinter();
        NewPrinter adapter = new PrinterAdapter(oldPrinter);
        adapter.printLine("Printed text.");
    }
}

class OldPrinter { // an existing class (incompatible interface)
    public void printText(String content) {
        System.out.println("Old Printer: " + content);
    }
}

interface NewPrinter { // a new expected interface
    void printLine(String content);
}

class PrinterAdapter implements NewPrinter {
    private final OldPrinter oldPrinter;

    PrinterAdapter(OldPrinter oldPrinter) {
        this.oldPrinter = oldPrinter;
    }

    @Override
    public void printLine(String content) {
        oldPrinter.printText(content); // adapting the old method
    }
}
```

<h2><a id="bridge">Bridge</a></h2>

<p>Bridge decouples (separates) abstraction from implementation, allowing them to vary independently and preventing a Cartesian complexity explosion (where the number of subclasses grows exponentially as new features are added). It acts as a bridge between high-level abstractions and concrete implementations by connecting these two hierarchies of different classes with a parameter.</p>

<p>The first hierarchy (```Sender``` and its implementations like ```FastSender``` and ```SecureSender```) represents the implementation. The second hierarchy (```Message``` and its subclasses like ```EmailMessage``` and ```SMSMessage```) represents the abstraction. The ```sender``` parameter in the ```Message``` constructor acts as a bridge that connects these two hierarchies dynamically.</p>

```java
public class Main {
    public static void main(String[] args) {
        // Cartesian combinations
        // FastSender EmailMessage
        // FastSender SMSMessage
        // SecureSender EmailMessage
        // SecureSender SMSMessage

        Sender fastSender = new FastSender();
        Sender secureSender = new SecureSender();

        Message email = new EmailMessage(fastSender);
        email.sendData("Hello via Email!");

        Message sms = new SMSMessage(secureSender);
        sms.sendData("Hello via SMS!");
    }
}

interface Sender {
    void sendData(String message);
}

class FastSender implements Sender {
    @Override
    public void sendData(String message) {
        System.out.println("Sending message quickly: " + message);
    }
}

class SecureSender implements Sender {
    @Override
    public void sendData(String message) {
        System.out.println("Sending message securely: " + message);
    }
}

abstract class Message { // a Bridge
    protected final Sender sender;

    Message(Sender sender) { // this parameter connects the two hierarchies
        this.sender = sender;
    }

    abstract void sendData(String content);
}

class EmailMessage extends Message {
    EmailMessage(Sender sender) {
        super(sender);
    }

    @Override
    void sendData(String content) {
        System.out.println("Sending Email:");
        sender.sendData(content);
    }
}

class SMSMessage extends Message {
    SMSMessage(Sender sender) {
        super(sender);
    }

    @Override
    void sendData(String content) {
        System.out.println("Sending SMS:");
        sender.sendData(content);
    }
}
```

<h2><a id="composite">Composite</a></h2>

<p>Composite treats individual objects and compositions of objects uniformly. It is commonly used in file systems to represent hierarchical structures where folders can contain both files and other folders. Instead of writing separate logic for handling individual files and directories, we use the same interface, making it easier to traverse and manage the entire structure.</p>

```java
import java.util.ArrayList;
import java.util.List;

public class Main {
    public static void main(String[] args) {
        Folder root = new Folder("Root");
        FileSystemItem file1 = new TextFile("file1.txt");
        FileSystemItem file2 = new TextFile("file2.txt");
        Folder subfolder = new Folder("Subfolder");
        subfolder.addItem(new TextFile("subfile.txt"));

        root.addItem(file1);
        root.addItem(subfolder);
        root.addItem(file2);
        root.display(0);
    }
}

interface FileSystemItem { // an interface (common for both files and folders)
    void display(int indent);
}

class TextFile implements FileSystemItem { // a leaf class (single file)
    private final String name;

    TextFile(String name) {
        this.name = name;
    }

    @Override
    public void display(int indent) {
        System.out.println(" ".repeat(indent) + "- " + name);
    }
}

class Folder implements FileSystemItem { // a Composite class (a folder that can contain files and other folders)
    private final String name;
    private final List<FileSystemItem> itemList = new ArrayList<>();

    Folder(String name) {
        this.name = name;
    }

    public void addItem(FileSystemItem item) {
        itemList.add(item);
    }

    @Override
    public void display(int indent) {
        System.out.println(" ".repeat(indent) + "[Folder] " + name);
        for (FileSystemItem item : itemList) // treating files and folders in the same way
            item.display(indent + 2);
    }
}
```

<h2><a id="decorator">Decorator</a></h2>

<p>Decorator allows dynamic addition of behavior to objects without altering their original code, enabling flexible and reusable functionality extension. It adheres to the OCP (new functionalities can be added via decorators) and the SRP (the new functionalities are kept separate).</p>

<p>The Decorator class is responsible for adding new behavior or functionality to an existing object dynamically, without modifying the object's original code, by wrapping the object and delegating method calls to it while potentially altering or enhancing the behavior.</p>

```java
public class Main {
    public static void main(String[] args) {
        // Creating a simple coffee
        Coffee simpleCoffee = new SimpleCoffee();
        System.out.println("Cost of simple coffee: " + simpleCoffee.cost());

        // Adding milk to the coffee using the MilkDecorator
        Coffee milkCoffee = new MilkDecorator(simpleCoffee); // MilkDecorator "wraps around" SimpleCoffee
        System.out.println("Cost of coffee with milk: " + milkCoffee.cost());
    }
}

interface Coffee { // an interface
    int cost();
}

class SimpleCoffee implements Coffee { // a concrete component
    @Override
    public int cost() {
        return 5; // the base cost of coffee
    }
}

class MilkDecorator implements Coffee { // a Decorator class
    private final Coffee coffee; // holding a reference to the coffee object

    MilkDecorator(Coffee coffee) {
        this.coffee = coffee;
    }

    // This decorator calls the cost() method from the wrapped object (SimpleCoffee) and adds the cost of milk
    @Override
    public int cost() {
        return coffee.cost() + 2; // adding the cost of milk to the coffee
    }
}
```

<p>The Java standard library uses this pattern in its I/O classes, e.g., ```new BufferedReader(new FileReader("file.txt"))``` wraps a ```FileReader``` object with a ```BufferedReader``` that adds buffering and the ```readLine()``` method. Java annotations (```@Annotation```) may look similar to decorators from other languages (e.g., Python), but they only add metadata to the code and don't change its behavior by themselves.</p>

<h2><a id="facade">Facade</a></h2>

<p>Facade provides a simplified interface to a larger, more complicated system, hiding the complexity and offering a higher-level API for clients. Optionally, we may wish to expose internals through the facade, e.g., for more detailed control or specific operations that bypass the simplified interface, allowing advanced users to interact directly with system components when necessary.</p>

```java
public class Main {
    public static void main(String[] args) {
        TV tv = new TV();
        SoundSystem soundSystem = new SoundSystem();
        StreamingService streamingService = new StreamingService();

        HomeTheaterFacade homeTheater = new HomeTheaterFacade(tv, soundSystem, streamingService);
        homeTheater.watchMovie(); // one call replaces multiple system interactions
        homeTheater.endMovie(); // one call shuts everything down
    }
}

class TV {
    public void turnOn() { System.out.println("TV is now ON"); }
    public void turnOff() { System.out.println("TV is now OFF"); }
}

class SoundSystem {
    public void turnOn() { System.out.println("Sound system is now ON"); }
    public void turnOff() { System.out.println("Sound system is now OFF"); }
}

class StreamingService {
    public void startMovie() { System.out.println("Streaming service is starting..."); }
    public void stopMovie() { System.out.println("Streaming service is stopping..."); }
}

class HomeTheaterFacade { // a Facade
    private final TV tv;
    private final SoundSystem soundSystem;
    private final StreamingService streamingService;

    HomeTheaterFacade(TV tv, SoundSystem soundSystem, StreamingService streamingService) {
        this.tv = tv;
        this.soundSystem = soundSystem;
        this.streamingService = streamingService;
    }

    public void watchMovie() {
        System.out.println("Starting movie mode...");
        tv.turnOn();
        soundSystem.turnOn();
        streamingService.startMovie();
        System.out.println("Movie is ready to watch!");
    }

    public void endMovie() {
        System.out.println("Shutting down movie mode...");
        streamingService.stopMovie();
        soundSystem.turnOff();
        tv.turnOff();
        System.out.println("Movie mode ended.");
    }
}
```

<h2><a id="flyweight">Flyweight</a></h2>

<p>Flyweight optimizes memory usage by sharing common object data, particularly for large numbers of similar objects (e.g., a database of users that can have the same names). It reduces the memory footprint by storing shared data externally and reusing common objects rather than creating new instances for each.</p>

<p>The Flyweight pattern typically has two parts: the Flyweight class, holding the shared data (intrinsic state), and the Flyweight Factory (or similar), responsible for creating and managing shared instances, ensuring that identical objects are reused instead of duplicated.</p>

```java
import java.util.HashMap;
import java.util.Map;

public class Main {
    public static void main(String[] args) {
        Name john1 = NameDatabase.fetchName("John");
        Name alice1 = NameDatabase.fetchName("Alice");

        // Reusing "John" and "Alice" from the database instead of creating new objects
        Name john2 = NameDatabase.fetchName("John");
        Name alice2 = NameDatabase.fetchName("Alice");

        john1.display("formal");
        john2.display("informal");
        alice1.display("formal");
        alice2.display("informal");

        // Checking whether the same instances were reused
        System.out.println(john1 == john2);
        System.out.println(alice1 == alice2);
    }
}

class Name { // a Flyweight class
    private final String name;

    Name(String name) {
        this.name = name;
    }

    public void display(String type) {
        System.out.println("Displaying " + name + " as " + type);
    }
}

class NameDatabase { // a Flyweight Factory
    private static final Map<String, Name> names = new HashMap<>();

    public static Name fetchName(String name) {
        return names.computeIfAbsent(name, Name::new); // creating a new object only if it doesn't exist yet
    }
}
```

<h2><a id="proxy">Proxy</a></h2>

<p>Proxy acts as an intermediary or placeholder for another object, controlling access. Proxies are used to add additional functionality or restrictions when interacting with objects, allowing for behaviors like access control, Lazy initialization, and resource optimization. There are different types of proxies, including Protection Proxy, which regulates access based on permissions or roles, and Virtual Proxy, which delays the creation of resource-intensive objects until they are needed, optimizing performance. A Virtual Proxy is one way to implement Lazy initialization, but, of course, Lazy initialization can be applied independently of Proxies.</p>

<h4>Protection Proxy</h4>

```java
public class Main {
    public static void main(String[] args) {
        AgeRestrictedMovie movie1 = new AgeRestrictedMovie(new Movie("Action movie", 18));
        System.out.println(movie1.watch(20));
        System.out.println(movie1.watch(16));

        AgeRestrictedMovie movie2 = new AgeRestrictedMovie(new Movie("Family movie", 0));
        System.out.println(movie2.watch(10));
    }
}

class Movie {
    private final String movieTitle;
    private final int rating;

    Movie(String movieTitle, int rating) {
        this.movieTitle = movieTitle;
        this.rating = rating;
    }

    public int getRating() { return rating; }

    public String watch() {
        return "Watching " + movieTitle;
    }
}

class AgeRestrictedMovie { // a Proxy
    private final Movie movie;

    AgeRestrictedMovie(Movie movie) {
        this.movie = movie;
    }

    public String watch(int age) {
        if (age >= movie.getRating())
            return movie.watch();
        else
            return "Age restriction: too young";
    }
}
```

<h4>Virtual Proxy</h4>

```java
public class Main {
    public static void main(String[] args) throws InterruptedException {
        VirtualProxy proxy = new VirtualProxy();

        System.out.println("Before accessing the resource...");
        System.out.println(proxy.display()); // heavy resource is loaded now, so it takes time
        System.out.println(proxy.display()); // resource is already loaded, no delay
    }
}

class HeavyResource {
    private final String data;

    HeavyResource() throws InterruptedException {
        System.out.println("Loading heavy resource...");
        Thread.sleep(2000);
        data = "Heavy resource loaded";
    }

    public String display() {
        return data;
    }
}

class VirtualProxy {
    private HeavyResource realResource;

    private HeavyResource loadResource() throws InterruptedException {
        if (realResource == null)
            realResource = new HeavyResource(); // Lazy initialization
        return realResource;
    }

    public String display() throws InterruptedException {
        return loadResource().display();
    }
}
```

<h5>Proxy VS Decorator</h5>

<p>Proxy provides an identical interface to the original object, focusing on controlling access or managing resources, while Decorator enhances the object's interface by adding new functionality. Decorator typically holds a reference to the object it decorates, whereas Proxy may not even interact with a materialized object, especially in cases like Lazy Initialization or access control. Essentially, Proxies manage access and resources, while Decorators extend behavior.</p>
