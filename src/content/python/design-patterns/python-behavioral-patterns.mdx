<p>Behavioral design patterns focus on the interaction and communication between objects. They aim to define how objects collaborate, ensuring efficient and flexible communication without tightly coupling components.</p>

<h2><a id="observer">Observer</a></h2>

<p>Observer allows a subject (publisher) to maintain a list of its dependents (observers) and automatically notify them of any state changes, usually by calling one of their methods. This pattern is typically used when changing one object requires changing others, and we want to avoid tight coupling between the objects.</p>

<h4>Event-based observer</h4>

<p>An event-based observer notifies subscribers when a specific event occurs, allowing dynamic reactions without directly monitoring a property change.</p>

```python
class Event(list): # inheriting from list to store subscribed observers
    def __call__(self, *args, **kwargs): # making the Event instance callable to trigger notifications
        for item in self: # looping through all subscribed observer functions
            item(*args, **kwargs) # calling each observer with the given arguments

class Subscriber:
    def __init__(self, name):
        self.name = name

    def receive_email(self, newsletter):
        print(f"{self.name} received: {newsletter}")

class Newsletter:
    def __init__(self):
        self.new_issue_released = Event()

    def release_new_issue(self, issue_title):
        print(f"Releasing new issue: {issue_title}")
        self.new_issue_released(issue_title)

john = Subscriber("John")
newsletter = Newsletter()
newsletter.new_issue_released.append(john.receive_email) # adding John to the subscription list

newsletter.release_new_issue("Design Patterns Vol. 1") # releasing a new issue
newsletter.new_issue_released.remove(john.receive_email) # removing John from the subscription list
newsletter.release_new_issue("Design Patterns Vol. 2") # releasing a new issue
```

<h4>Property observer</h4>

<p>A property observer ties event handling to a property change (using ```@property``` and ```@setter```). It is just a different approach to the Observer pattern. Both are good, and we just have to choose the one that suits our needs.</p>

```python
class Event(list):
    def __call__(self, *args, **kwargs):
        for item in self:
            item(*args, **kwargs)

class Subscriber:
    def __init__(self, name):
        self.name = name

    def receive_email(self, newsletter):
        print(f"{self.name} received: {newsletter}")

class Newsletter:
    def __init__(self):
        self._new_issue = None
        self.new_issue_released = Event() # the event fires when issue updates

    @property
    def new_issue(self):
        return self._new_issue

    @new_issue.setter
    def new_issue(self, issue_title):
        if self._new_issue != issue_title: # ensuring it's actually changing
            self._new_issue = issue_title
            print(f"New issue set: {issue_title}")
            self.new_issue_released(issue_title) # notifying subscribers

john = Subscriber("John")
newsletter = Newsletter()
newsletter.new_issue_released.append(john.receive_email)

newsletter.new_issue = "Design Patterns Vol. 1" # automatically notifying John
newsletter.new_issue_released.remove(john.receive_email)
newsletter.new_issue = "Design Patterns Vol. 2" # no notification sent
```

<h4>Property dependencies</h4>

<p>Property dependencies ensure that when a property changes, the properties that depend on it (e.g., age depends on the current year) notify their observers too, even though they are never set directly.</p>

```python
class Event(list):
    def __call__(self, *args, **kwargs):
        for item in self:
            item(*args, **kwargs)

class Person:
    def __init__(self, birth_year, current_year):
        self.birth_year = birth_year
        self._current_year = current_year
        self.property_changed = Event()

    @property
    def age(self):
        return self._current_year - self.birth_year

    @property
    def current_year(self):
        return self._current_year

    @current_year.setter
    def current_year(self, value):
        old_age = self.age
        self._current_year = value
        if self.age != old_age:
            self.property_changed("age", old_age, self.age) # age depends on current_year, so its change is announced too

person = Person(2000, 2025)
person.property_changed.append(lambda name, old, new: print(f"{name} changed from {old} to {new}"))

person.current_year = 2030 # notifying about the age change
person.current_year = 2030 # no notification (the age didn't change)
```

<h2><a id="chain-of-responsibility">Chain of Responsibility</a></h2>

<p>Chain of Responsibility allows multiple handlers to process a request without the sender needing to know which handler will handle it. The request is passed along a chain of handlers until one of them processes it (or it reaches the end of the chain). This pattern promotes loose coupling and makes it easy to add or modify handlers dynamically. All components of a chain get a chance to process a command or a query, and have the ability to terminate the processing chain.</p>

<h4>Method chain (classic approach)</h4>

<p>In this approach, each handler explicitly calls the next one. It is good for request approval flows.</p>

```python
class Request:
    def __init__(self, amount):
        self.amount = amount

class Handler:
    def __init__(self, successor = None):
        self.successor = successor

    def handle(self, request):
        if self.successor:
            self.successor.handle(request)

class Manager(Handler):
    def handle(self, request):
        if request.amount <= 1000:
            print(f"Manager approves ${request.amount}")
        else:
            super().handle(request)

class Director(Handler):
    def handle(self, request):
        if request.amount <= 5000:
            print(f"Director approves ${request.amount}")
        else:
            super().handle(request)

class CEO(Handler):
    def handle(self, request):
        if request.amount > 5000:
            print(f"CEO approves ${request.amount}")

# Creating the chain: Manager -> Director -> CEO
manager = Manager(Director(CEO()))

# Requests go through the chain until handled
manager.handle(Request(500)) # handled by Manager
manager.handle(Request(3000)) # handled by Director
manager.handle(Request(10000)) # handled by CEO
```

<h4>Broker chain (event-based approach)</h4>

<p>Broker chain uses an event-driven system where multiple handlers process a request independently without forming a strict chain. It is useful in scenarios where multiple components modify a value dynamically, such as game stat modifiers or discount systems in e-commerce. Even though handlers are not explicitly linked, they act on the request in sequence when the event is triggered. It is a more flexible and decentralized version of the Chain of Responsibility pattern.</p>

<p>In the example below, ```ECommercePlatform``` is the broker. Handlers subscribe to it, and every price request is passed as a ```Query``` object through all of them.</p>

```python
class Product:
    def __init__(self, name, base_price):
        self.name = name
        self.base_price = base_price

class Query:
    def __init__(self, product_name, value):
        self.product_name = product_name
        self.value = value

class ECommercePlatform: # a broker
    def __init__(self):
        self.handlers = []

    def subscribe(self, handler):
        self.handlers.append(handler)

    def get_price(self, product):
        query = Query(product.name, product.base_price)
        for handler in self.handlers: # every handler gets the query and may modify its value
            handler.handle(query)
        return query.value

class BlackFridayDiscount:
    def __init__(self, product_name):
        self.product_name = product_name

    def handle(self, query):
        if query.product_name == self.product_name:
            query.value *= 0.8 # 20% discount

class LoyaltyDiscount:
    def __init__(self, product_name):
        self.product_name = product_name

    def handle(self, query):
        if query.product_name == self.product_name:
            query.value *= 0.9 # additional 10% discount for loyal customers

platform = ECommercePlatform()
laptop = Product("Laptop", 1000)

print("Original price:", platform.get_price(laptop))

platform.subscribe(BlackFridayDiscount("Laptop"))
print("After Black Friday discount:", platform.get_price(laptop))

platform.subscribe(LoyaltyDiscount("Laptop"))
print("After loyalty discount:", platform.get_price(laptop))
```

<h2><a id="command">Command</a></h2>

<p>Command is used to turn a request (an action) into a stand-alone object. This object encapsulates all details of the request, allowing parameterization of objects. It is also useful for, e.g., implementing the undo functionality.</p>

<p>In the example below, ```DepositCommand``` encapsulates the action and its details (the account and the amount), and ```BankAccount``` (the receiver) performs it. ```CommandHistory``` (the invoker) executes Commands and keeps them on a stack, so the most recent one can be undone.</p>


```python
from abc import ABC, abstractmethod

class Command(ABC):
    @abstractmethod
    def execute(self):
        pass

    @abstractmethod
    def undo(self):
        pass

class BankAccount: # a receiver (the object that performs the action)
    def __init__(self):
        self.balance = 0

    def deposit(self, amount):
        self.balance += amount

    def withdraw(self, amount):
        self.balance -= amount

class DepositCommand(Command): # a concrete Command (the action and its details)
    def __init__(self, account, amount):
        self.account = account
        self.amount = amount

    def execute(self):
        self.account.deposit(self.amount)

    def undo(self):
        self.account.withdraw(self.amount)

class CommandHistory: # an invoker (executes Commands and remembers them)
    def __init__(self):
        self.history = []

    def execute(self, command):
        command.execute()
        self.history.append(command)

    def undo(self):
        if self.history:
            self.history.pop().undo() # undoing the most recent Command

account = BankAccount()
history = CommandHistory()

history.execute(DepositCommand(account, 100))
history.execute(DepositCommand(account, 50))
print(account.balance) # 150

history.undo() # undoing the last deposit
print(account.balance) # 100
```

<h2><a id="interpreter">Interpreter</a></h2>

<p>Interpreter is used for designing a system that needs to process and evaluate language expressions. It provides a way to define the grammar of a language and interpret statements in that language. It is commonly used in mathematical expression evaluators, rule-based engines, and parsers. It turns text data into separate lexical tokens (lexing) and interprets sequences of these tokens (parsing).</p>

<p>The example below implements a simple interpreter for arithmetic expressions that includes addition and subtraction. It tokenizes an expression like "10 + 5 - 3", parses it into an abstract syntax tree (AST), and evaluates the result. Each grammar rule (a number or a binary operation) is represented by a class with an ```evaluate()``` method, and evaluating the tree means calling ```evaluate()``` on its root, which recursively evaluates its children.</p>

```python
class Num:
    def __init__(self, value):
        self.value = value

    def evaluate(self):
        return self.value

    def __repr__(self):
        return f"Num({self.value})"

class BinaryOperation:
    def __init__(self, left, operator, right):
        self.left = left
        self.operator = operator
        self.right = right

    def evaluate(self):
        if self.operator == "+":
            return self.left.evaluate() + self.right.evaluate()
        return self.left.evaluate() - self.right.evaluate()

    def __repr__(self):
        return f"BinaryOperation({self.left}, {self.operator}, {self.right})"

def parse(tokens): # parsing: building the tree from left to right: ((10 + 5) - 3)
    result = Num(int(tokens[0]))
    for i in range(1, len(tokens), 2):
        result = BinaryOperation(result, tokens[i], Num(int(tokens[i + 1])))
    return result # returning the root of the AST

tokens = "10 + 5 - 3".split() # lexing: splitting the text into tokens
print(tokens)

ast = parse(tokens)
print(ast)
print(ast.evaluate())
```

<h2><a id="iterator">Iterator</a></h2>

<p>Iterator provides a way to access elements of a collection sequentially without exposing its underlying structure. Instead of manually managing iteration, the pattern encapsulates it within an iterator object that keeps track of the current position and provides a standard way to retrieve the next element. In Python, every object with an ```__iter__()``` method (returning an iterator object with a ```__next__()``` method) can be used in a ```for``` loop. In the example below, ```Inventory``` stores its items in a list, but the client goes through them only with a custom iterator and never accesses the list directly. In practice, ```__iter__()``` is often written as a generator instead (check out the <a href="/tutorials/python/python-generators#iterator" class="link">lesson about generators</a>).</p>

```python
class InventoryIterator: # an Iterator that keeps track of the current position
    def __init__(self, list_items):
        self._list_items = list_items
        self._index = 0

    def __iter__(self):
        return self

    def __next__(self):
        if self._index >= len(self._list_items):
            raise StopIteration
        item = self._list_items[self._index]
        self._index += 1
        return item

class Inventory:
    def __init__(self, *list_items):
        self._list_items = list(list_items)

    def __iter__(self):
        return InventoryIterator(self._list_items)

inventory = Inventory("Sword", "Shield", "Potion")

iterator = iter(inventory) # using the Iterator manually
print(next(iterator))
print(next(iterator))
print(next(iterator))

for item in inventory: # the for loop calls iter() and next() under the hood
    print(item)
```

<h2><a id="mediator">Mediator</a></h2>

<p>Mediator defines an object that encapsulates how a set of objects interact. Instead of having multiple objects communicate directly, they communicate through a mediator, which handles the communication and coordination between them. This reduces the dependencies between objects, making the system easier to maintain and scale (the objects do not have to be aware of the other objects).</p>

```python
from abc import ABC, abstractmethod

class Mediator(ABC):
    @abstractmethod
    def send_data(self, message, sender):
        pass

class User:
    def __init__(self, name):
        self.name = name
        self.mediator = None

    def send_message(self, message):
        print(f"{self.name} sends: {message}")
        self.mediator.send_data(message, self)

    def receive_message(self, message):
        print(f"{self.name} receives: {message}")

class ChatRoom(Mediator):
    def __init__(self):
        self.users = []

    def add_user(self, user):
        self.users.append(user)
        user.mediator = self # setting the chat room as the mediator for each user when they join it

    def send_data(self, message, sender):
        for u in self.users:
            if u != sender:
                u.receive_message(message)

chat_room = ChatRoom()

alice = User("Alice")
bob = User("Bob")
charlie = User("Charlie")

chat_room.add_user(alice)
chat_room.add_user(bob)
chat_room.add_user(charlie)

alice.send_message("Hi everyone!")
bob.send_message("Hello Alice!")
charlie.send_message("Hey all!")
```

<h2><a id="memento">Memento</a></h2>

<p className="noBottomMargin">Memento saves an object's state so that it can be restored later, without exposing how the object stores that state. It is the basis of undo/redo functionality and checkpoints (save points). It has three parts:</p>
<ul>
    <li><b>Originator</b> (```TextEditor```) - the object whose state we want to save. Its ```save()``` method returns a Memento with the current content, and its ```restore()``` method sets the content back from a given Memento.</li>
    <li><b>Memento</b> - a snapshot of the originator's state at one moment (here, the text in the editor).</li>
    <li><b>Caretaker</b> (```History```) - decides when to save and restore the state (```backup()```, ```undo()```, and ```redo()```) and stores the Mementos on undo and redo stacks, but never reads or changes their contents.</li>
</ul>

```python
class Memento: # a snapshot of the editor's state
    def __init__(self, content):
        self._content = content # only TextEditor should read it

class TextEditor: # an originator
    def __init__(self):
        self.content = ""

    def write(self, text):
        self.content += text

    def save(self):
        return Memento(self.content)

    def restore(self, memento):
        self.content = memento._content

    def show_content(self):
        print(f"Document content: {self.content}")

class History: # a caretaker
    def __init__(self, editor):
        self.editor = editor
        self.undo_stack = []
        self.redo_stack = []

    def backup(self):
        self.undo_stack.append(self.editor.save())
        self.redo_stack.clear() # a new change discards the states that could be redone

    def undo(self):
        if self.undo_stack:
            self.redo_stack.append(self.editor.save())
            self.editor.restore(self.undo_stack.pop())

    def redo(self):
        if self.redo_stack:
            self.undo_stack.append(self.editor.save())
            self.editor.restore(self.redo_stack.pop())

editor = TextEditor()
history = History(editor)

history.backup()
editor.write("Hello, ")
editor.show_content() # "Hello, "

history.backup()
editor.write("world!")
editor.show_content() # "Hello, world!"

history.undo()
editor.show_content() # "Hello, "
history.redo()
editor.show_content() # "Hello, world!"
```

<h2><a id="state">State</a></h2>

<p>State allows an object to change its behavior when its internal state changes. It encapsulates different behaviors within separate state classes, making the system more maintainable and flexible.</p>

<p>In the example below, the behavior that changes is how the ```TrafficLight``` object responds to the ```change()``` method, depending on its current state. The ```change()``` method passes the call to the ```switch_light()``` method of the current state, and each state class defines its own transition: ```RedState``` switches the light to green, ```GreenState``` to yellow, and ```YellowState``` to red.</p>

```python
from abc import ABC, abstractmethod

class TrafficLightState(ABC): # a State interface
    @abstractmethod
    def switch_light(self, light):
        pass

# Concrete State classes
class RedState(TrafficLightState):
    def switch_light(self, light):
        print("Red -> Switching to Green")
        light.state = GreenState()

class YellowState(TrafficLightState):
    def switch_light(self, light):
        print("Yellow -> Switching to Red")
        light.state = RedState()

class GreenState(TrafficLightState):
    def switch_light(self, light):
        print("Green -> Switching to Yellow")
        light.state = YellowState()

class TrafficLight: # a context class (the object that maintains the current state and triggers state transitions)
    def __init__(self):
        self.state = RedState() # an initial State

    def change(self):
        self.state.switch_light(self) # switching the State by executing the switch_light() method from the current State class

traffic_light = TrafficLight()
traffic_light.change()
traffic_light.change()
traffic_light.change()
```

<h2><a id="strategy">Strategy</a></h2>

<p>Strategy defines a family of algorithms, encapsulates each one in a separate class, and allows them to be interchangeable without modifying the client code. This enables selecting an algorithm dynamically at runtime, promoting flexibility and maintainability.</p>

```python
from abc import ABC, abstractmethod

class RouteStrategy(ABC): # a Strategy interface
    @abstractmethod
    def travel_time(self, distance_km): # in minutes
        pass

# Concrete Strategy classes
class CarRoute(RouteStrategy):
    def travel_time(self, distance_km):
        return distance_km * 60 // 50 # 50 km/h

class WalkingRoute(RouteStrategy):
    def travel_time(self, distance_km):
        return distance_km * 60 // 5 # 5 km/h

class Navigator: # a context class
    def __init__(self, strategy: RouteStrategy):
        self.strategy = strategy

    def set_strategy(self, strategy: RouteStrategy):
        self.strategy = strategy # changing Strategies dynamically

    def estimate(self, distance_km):
        return f"{distance_km} km takes {self.strategy.travel_time(distance_km)} minutes"

navigator = Navigator(CarRoute())
print(navigator.estimate(30))

navigator.set_strategy(WalkingRoute())
print(navigator.estimate(30))
```

<h2><a id="template-method">Template Method</a></h2>

<p>Template Method defines the skeleton of an algorithm in a base class while allowing subclasses to fill in specific steps. This promotes code reuse and ensures that the core logic remains unchanged while allowing flexibility in certain steps.</p>

```python
from abc import ABC, abstractmethod

class ReportTemplate(ABC):
    def generate_report(self): # a Template Method defining the steps for generating a report
        self.collect_data()
        self.analyse_data()
        print("Done.")
        
    @abstractmethod
    def collect_data(self):
        pass

    @abstractmethod
    def analyse_data(self):
        pass

class SalesReport(ReportTemplate):
    def collect_data(self):
        print("Collecting sales data...")

    def analyse_data(self):
        print("Analyzing sales trends...")

class InventoryReport(ReportTemplate):
    def collect_data(self):
        print("Collecting inventory data...")

    def analyse_data(self):
        print("Checking stock levels...")

sales = SalesReport()
sales.generate_report()

inventory = InventoryReport()
inventory.generate_report()
```

<h2><a id="visitor">Visitor</a></h2>

<p>Visitor separates operations (algorithms) from the object structure they work on. Instead of putting every operation inside the element classes, each operation is placed in a separate Visitor class that visits the elements. As a result, new operations can be added without modifying the existing classes (in compliance with the OCP), and the document structure stays unchanged.</p>

<p className="noBottomMargin">Instead of adding new methods to ```TextElement``` and ```ImageElement``` every time we need a new operation, we simply create a new Visitor class that implements those operations without modifying the element classes. This pattern relies on double dispatch, where both the element type (```TextElement``` or ```ImageElement```) and the visitor type (```Renderer``` or ```WordCounter```) determine the behavior, meaning:</p>

<ol>
    <li>The element calls its ```accept(visitor)``` method, passing the visitor as an argument.</li>
    <li>Inside ```accept(visitor)```, the element calls the visitor’s corresponding method (```visit_text()``` or ```visit_image()```), passing itself (```self```) as an argument.</li>
    <li>The visitor determines what to do based on the element type.</li>
</ol>

```python
from abc import ABC, abstractmethod

class DocumentElement(ABC): # an element interface
    @abstractmethod
    def accept(self, visitor):
        pass

# Concrete elements
class TextElement(DocumentElement):
    def __init__(self, text):
        self.text = text

    def accept(self, visitor):
        visitor.visit_text(self)

class ImageElement(DocumentElement):
    def __init__(self, file_name):
        self.file_name = file_name

    def accept(self, visitor):
        visitor.visit_image(self)

class Visitor(ABC): # a Visitor interface
    @abstractmethod
    def visit_text(self, element):
        pass

    @abstractmethod
    def visit_image(self, element):
        pass

# Concrete Visitors
class Renderer(Visitor):
    def visit_text(self, element):
        print(f"Rendering text: {element.text}")

    def visit_image(self, element):
        print(f"Rendering image: {element.file_name}")

class WordCounter(Visitor):
    def __init__(self):
        self.total = 0

    def visit_text(self, element):
        self.total += len(element.text.split())

    def visit_image(self, element):
        pass # images have no words

elements = [TextElement("Design patterns are useful"), ImageElement("diagram.png"), TextElement("Hello world")]

renderer = Renderer()
word_counter = WordCounter()
for element in elements:
    element.accept(renderer)
    element.accept(word_counter)
print(f"Total words: {word_counter.total}")
```

<h5>Visitor VS Decorator</h5>

<p>A Visitor allows new operations to be added to an existing object structure without modifying the element classes, by separating operations from the objects they operate on. Decorator allows existing behavior to be extended or modified by wrapping an object with another object that implements the same interface.</p>
